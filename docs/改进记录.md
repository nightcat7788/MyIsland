## 一、本轮共 7 处改动

### 1. PromptTimer：指针/悬停计时不再受 WM_TIMER 饥饿影响
- **来源**：BrimDeck `src/BrimDeck/PromptTimer.cs`
- **问题**：WPF 的 `DispatcherTimer` 骑在 WM_TIMER 上，Windows 只在消息队列空闲时才生成 WM_TIMER——鼠标持续移动时 tick 最迟到 3.5 秒才来，悬停展开因此会"迟钝"。
- **改动**：
  - 新增 `src/Island.App/Services/PromptTimer.cs`：线程池计时器驱动，每次 tick 用 `Dispatcher.BeginInvoke` 投递回 UI 线程；**至多一个 tick 在等**（UI 忙时只补一次，不积压）；**代号守卫**（Start/Stop 后已投递未执行的 tick 作废）；`Dispose` 释放。
  - `Controls/IslandWindow.xaml.cs:31-33, 96-97, 211-213`：`_pointerTrack`（30ms）由 `DispatcherTimer` 换成 `PromptTimer`；窗口关闭时 Stop+Dispose。
  - 低频工作保持 `DispatcherTimer`：全屏检测 1s、天气 30min、视图轮换 30s。
- **未改**：16ms 动画帧循环。理由：`Frame_Tick` 用固定 `dt=1/60` 步进弹簧，`CompositionTarget.Rendering` 的刷新率不确定（60/120/144Hz），会改变弹簧推进速度——数学不变是红线，收益不足以抵消风险。**这仍是已知项**：动画帧循环仍可能受消息队列繁忙影响。

### 2. 设置持久化加固（损坏隔离 / 未知字段保留 / 防抖写）
- **来源**：BrimDeck `src/BrimDeck.Core/Settings.cs` 的 `SettingsStore`
- **问题**：原来的 `Settings.Load()` 读失败会**静默用默认值**，用户的设置全部丢失且没有任何痕迹；不认识的文件字段会被旧版本抹掉；每点一次设置就写一次盘。
- **改动**（`src/Island.App/Services/Settings.cs`）：
  - **损坏隔离**：读失败时把原文件**复制**为 `settings.unreadable-<yyyyMMdd-HHmmss>.json`（同秒重名追加序号），**原文件既不覆盖也不删除**，再用默认值。
  - **未知字段保留**：用 `JsonNode` 读成"已知属性 + 未知键"，保存时把未知键原样写回。
  - **防抖 + 串行**：新增 `RequestSave()`（400ms 合并连续改动，只落一次盘），`Save()` 保持**立即写**语义（退出/显式保存仍用它），写盘用静态锁串行。
  - `Controls/SettingsWindow.cs`：逐项开关改用 `RequestSave()`；"完成/关闭/重置"仍用 `Save()`。
- **新增测试**：见第 5 项（42 条断言里有 20 条是设置的）。

### 3. 启动分步容错：某一步失败不再拖垮整个启动
- **来源**：BrimDeck `src/BrimDeck/App.xaml.cs` 的 `App.Step`
- **问题**：以前 `OnStartup` 是一整段顺序执行，中途抛异常就跳过后面全部步骤——岛体窗口一失败，**托盘图标、右键菜单、设置中心全都没有**，用户既进不去设置也退不出进程。
- **改动**（`src/Island.App/App.xaml.cs`）：启动拆成 9 步（`Step("名字", 动作)`），每步独立 try/catch 并写进 crash.log：
  DPI 感知 → 单实例互斥 → 异常捕获 → 二次启动唤起通道 → 加载设置 → **创建并显示岛体窗口** → 设置托盘图标 → 右键菜单 → 设置中心。
  **关键收益**：岛体窗口失败时，托盘照样出现，用户仍能从托盘退出/打开设置。

### 4. 二次启动唤起已有实例
- **来源**：BrimDeck 用 `EventWaitHandle` 做"第二次启动唤起第一个实例"
- **改动**（`App.xaml.cs` + `IslandWindow.xaml.cs`）：
  - 第一个实例建 `Local\MyIsland.Relaunch.<用户名>` 事件并注册等待；第二个实例 `OpenExisting().Set()` 成功后**静默退出**（不再弹"已在运行"提示框），失败才退回提示框。
  - 互斥体名也改为带用户名（`Local\MyIsland.Instance.<用户名>`），多用户机器各跑各的，互不锁死。
  - 新增 `IslandWindow.ShowAndExpand()`：**展开到**展开态，而不是 `ToggleExpand()` 切换（已经是展开态时不该被收起）。
  - **唤起后保持展开**：唤起时鼠标多半不在岛体上，不锁住的话悬停收起逻辑 350ms 后又把它关回去，等于白唤起。新增 `_keepOpenUntilHover`：唤起后保持展开，直到鼠标真的移进岛体，再恢复正常悬停规则。
  - 唤起信号早于岛体窗口建成时用 `_relaunchPending` 兜住，窗口一出现就补做。

### 5. 最小测试门禁（本项目此前**完全没有测试**）
- **来源**：BrimDeck 的三套自研 harness（`tests/BrimDeck.Tests` 等）
- **改动**：
  - 新增 `tests/Island.Tests/`：`OutputType=Exe`、`net8.0-windows`、`UseWPF=true`、**零 NuGet 依赖**；用 `Compile Include` 把 `Settings.cs`、`Island.Core/Monitoring/*.cs`、`Theme.cs` 链进测试工程（与主工程"源码合并进单一 exe"的思路一致）。
  - harness 写法仿 BrimDeck：`Check(name, condition)` 失败即抛、逐条打印 `PASS:`、失败时 `Environment.ExitCode = 1`。
  - **42 条断言**（设置 20 / 主题 9 / 监控模型 13），全部通过。
  - `Island.sln` 加入测试工程；`dev.ps1` 在**发布之前**加一步"跑测试"，失败即中止发布。

### 6. 常驻应用的 GC 与发布调优
- **来源**：BrimDeck `src/BrimDeck/BrimDeck.csproj`
- **改动**（`src/Island.App/Island.App.csproj`）：
  - `ConcurrentGarbageCollection=false`、`System.GC.ConserveMemory=5`、`System.GC.Gen0MaxBudget=4194304`（4MB）：岛体长期挂在桌面顶层，大部分时间不动，静止时分配的读数/天气对象很快填满最年轻代，而它们都算在工作集里；这一代回收不到 1 毫秒。
  - 发布版（带 RuntimeIdentifier）`TieredCompilation=false`：关掉"启动几分钟后后台重编译热方法"（表现为首次展开面板的 CPU 突刺），代价是冷启动略慢，对常驻应用是净收益。
  - 发布版 `PublishReadyToRun=true`（composite 关）：与自定义 ALC 的"按字节加载"路径**实测兼容**（见验证）。
  - `DefaultItemExcludes` + `<Compile Remove="obj\**;bin\**">`：publish 生成的 `*.g.cs` 在重定向中间输出目录时会被当成源码二次编译（600+ 重复定义错误），显式排除后两种构建方式都干净。

### 7. 开发脚本的机器无关性（顺手修的真 bug）
- `tools/start-island.ps1` 原来**写死了作者另一台机器的路径**（`C:\Users\fengl\WorkBuddy\...\run.ps1` 和一个本机不存在的 pwsh 应用别名）——换台机器开发循环永远起不来。现在：路径按 `$PSScriptRoot` 推导；优先找 pwsh 走内存加载，找不到就直跑 `Island.App.exe`。
- `dev.ps1` / `sign.ps1` 补 **UTF-8 BOM**：无 BOM 的 UTF-8 脚本在 Windows PowerShell 5.1 下会按 ANSI 代码页解码，中文注释里的字节可能破坏语法（实测 `dev.ps1` 直接解析失败）。补 BOM 后 4 个 ps1 全部语法检查通过。

## 三、遗留与下一批候选

**已知遗留**
1. 16ms 动画帧循环仍是 `DispatcherTimer`（固定 dt 步进弹簧，改 `CompositionTarget.Rendering` 会改变弹簧速度），故消息队列繁忙时动画仍可能掉帧。
2. 换用 `_frame` 之外的 `DispatcherTimer`（1s/30s/30min）保持不变——低频晚一点无妨，与 BrimDeck 的分法一致。
3. 互斥体改名带用户名后，与旧版本并存时可能短暂出现两个实例（老进程退出即恢复）。
4. 设置损坏时是"复制副本 + 原文件留在原地"，下次成功保存会覆盖原文件（原始字节始终在 unreadable 副本里）。若要求原文件必须被移走，改 `KeepUnreadable()` 一行即可。
5. 未提交：改动都留在工作区（按约定不自动 commit）。

**下一批候选（按价值/成本排序）**
1. **按需采集闸门**：BrimDeck 用"谁需要读什么"的集合决定采样，没选中的读数根本不读。MyIsland 监控页可照此收紧（当前仍有固定间隔的全量采样）。
2. **设置的版本号与有序迁移**：加 `Version` 字段 + 迁移步骤，并让 CI 校验"新增迁移步骤必须与目标分支版本号匹配"（BrimDeck 的 `Test-MigrationVersions.ps1`）。
3. **剪贴板图片处理移出 UI 线程** + 富文本与纯文本统一落盘判定（BrimDeck 现状有这两个坑，别照抄）。
4. **发布包哈希清单 + 安装/更新/卸载自动化验证脚本**（BrimDeck 的 `Test-AppUpdate.ps1`）。
5. **凭据 `ToString()` 防泄密**：将来若加 API Key/Token，承载它的 record 一律重写 `ToString()`。

## 五、蓝屏 bug:提权后整机重启(0x1EA)—— 根因与修复 (2026-11-23)

### 现象
以管理员重启 MyIsland(托盘菜单"以管理员重启")后,**机器直接蓝屏重启**。系统事件日志三次同一 bugcheck:

| 时间 | bugcheck | 含义 |
|---|---|---|
| 2026-11-22 13:52 | 0x000001EA | THREAD_STUCK_IN_DEVICE_DRIVER |
| 2026-11-22 14:05 | 0x000001EA | 同上 |
| 2026-11-23 04:13 | 0x000001EA | 同上 |

前两次作者已定位到 **LHM 存储传感器(NVMe SMART IOCTL)**,已把 `IsStorageEnabled=false` 永久关闭。第三次(11/23)是**另一个原因**,本次定位的就是它。

### 证据链
1. **物证时间戳**:`C:\Windows\System32\drivers\inpoutx64.sys` 的 **CreationTime = 11/22 14:04:49**(= 第二次蓝屏前 31 秒)、LastWriteTime = **11/23 04:15:24**(= 第三次蓝屏的崩溃窗口)。这个驱动不是系统自带的。
2. **谁装它**:随包发布的 `inpoutx64.dll` 里含 `CreateService` / `StartService` / `OpenSCManager` / `inpoutx64.sys`(UTF-16)—— **它一被 LoadLibrary 就会把未签名驱动落地并加载**(签名状态:空/未签名)。
3. **谁加载它**:全库只有 `InpOutSmnService` 会 `LoadLibrary("inpoutx64.dll")`;而它只在**管理员**下才真正走到 `MapPhysToLin`(普通用户映射失败 → 优雅退出)。**"提权才崩"由此解释。**
4. **崩在哪一步**:`MapPhysToLin` 把 **PCIe ECAM / MMIO 物理区(0xE0000000 / 0xC0000000 / 0xF0000000)** 映射进进程并读取。本机是 **Intel Core Ultra 5 225H + Arc 130T**:0xE0000000 正是它的 ECAM,0xC0000000 常是核显 BAR——**映射+读就把 PCIe 主机桥/核显拖死**,调用线程再也回不来 → 0x1EA。
5. **致命顺序**:厂商判断(`0x1022` = AMD)原本在**映射之后**才做;而 SMN(SMN index `0x59800`)本就是 **AMD 专有**——在 Intel 上这条路径**永远读不到温度**(诊断日志:"ECAM probe fail"),**零收益、整机风险**。
6. **排除项**:LHM 0.9.6 用的是**微软签名的 PawnIO**(`LibreHardwareMonitor.Resources.PawnIo.*.bin`),不是 InpOut/WinRing0 → **LHM 不是元凶**。

### 修复(按根因,不是症状)
| 位置 | 改动 |
|---|---|
| `Services/InpOutSmnService.cs` | ① **厂商门控前置**:`LoadLibrary` **之前**用注册表 `VendorIdentifier` 判 AMD,非 AMD 直接返回("not AMD (SMN is AMD-only) - skipped before loading the driver")——绝不加载 dll、绝不装驱动、绝不映射物理内存。② **不猜基址**:只保留 0xE0000000(AMD Zen 的 ECAM 标准基址),去掉 0xC0000000 / 0xF0000000(显卡 BAR / 其它 MMIO 区)。③ 非 Windows 平台编译为空实现(Mac 版不受影响)。 |
| `Services/ThermalService.cs` | SMN 通道改为 **`AllowSmnDirectRead` 显式开启**才创建/使用;诊断行如实写明"disabled" |
| `Services/Settings.cs` | 新增 `EnableSmnDirectRead`(默认 **false**) |
| `Controls/SettingsWindow.cs` | 设置中心 › 监控 › 新增"高风险实验功能"卡片:说明文字 + 开关(默认关) |
| `Island.App.csproj` | **不再随包发布 inpoutx64.dll**(用户机器上不该留着一个"一加载就装未签名驱动"的文件) |
| `tests/Island.Tests/ThermalChannelTests.cs` | **回归测试**:非 AMD 机器上 SMN 通道必须在加载驱动前拒绝,且**不得落地/改动 inpoutx64.sys**;厂商判定与注册表交叉验证 |
| `SOURCE-README.txt` | 温度链路说明改成当前事实 + 两次 0x1EA 教训 |

### 修复后的温度来源(优先级)
1. **LHM + PawnIO**(微软签名的驱动,需管理员)→ 2. **WMI 热区** → 3. 都没有就显示 **"--"**,绝不伪造。
   (SMN 直读默认关闭;AMD 用户可在设置里自行开启并自备 dll。)

### 验证
- 解决方案构建 **0 警告 0 错误**(含跨平台的 Avalonia 工程);测试 **49 条全通过**(新增 4 条:SMN 回归 3 条 + 默认开关 1 条)。
- 自包含发布成功,发布目录**不再包含 inpoutx64.dll**。
- 实机启动:温度诊断输出 `SMN-inpoutx64: disabled (EnableSmnDirectRead=off)`;**`inpoutx64.sys` 的时间戳完全没变**(证明没有落地/加载驱动);系统里只剩微软签名的 PawnIO。

## 六、清理残留驱动 + 管理员启动稳定性复测 (2026-11-23 04:38–04:47)

### 峰值内存的根因

不可预测地申请 700 MB – 4.5 GB 提交内存再立刻释放。重复实验里只做这一步，三次峰值都是 4,143 MB；与 WPF、
与初始化顺序都无关。而只有核显的机器上它一个读数都不产生：库枚举到的唯一设备是核显，被库自己跳过；
核显的显存 / 功耗 / 时钟走的是 D3D 那条路（55 ms，没有尖峰）。

#### 展开态 CPU：怎么查出来的

- **诊断构建**（只在临时副本里，不进产品）：给渲染路径加计数器和计时器（画布重绘、监控页重绘、帧循环、面板布局、
  毛玻璃截图 / 换图），每 5 秒把进程 CPU **按线程**导出一次。比看任务管理器的总数有用得多：一眼能看出
  哪个线程在忙、它在忙什么。
- **查到的**：监控页重绘一次约 30 ms（录制绘制指令约 5 ms + 软件光栅化约 25 ms），重做前后一样，是展开态最大的一块。
  温度服务每 1.4 秒推一次快照，每次都让监控页整页重绘 —— 每 5 秒 3–4 次，其中只有 1 次是因为监控快照变了。
  非管理员时温度位一直是"需管理员"，这些重绘全是白画。
- **修法 1**：`Controls/ThermalDisplay.Signature` 把一份温度快照算成"这一页看得见的样子"（取整后的温度 / 功耗、
  一位小数的显存，与 OnRender 的显示格式逐项对应）。`MonitorPage.ThermalUpdate` 拿它和"上一次真正画上去的"比，
  画面会变才 `InvalidateVisual`。改监控页里温度的显示格式时要同步改它，DesignSystemTests 守着取整边界。
- **修法 2**：限宽省略的文本（6 个进程名 + 显卡名）按"文本 + 可用宽度"缓存。原来每次重绘都重新排版这 7 段，
  离屏探针实测约 3 ms，占一次"读数没变"的重绘的大半。
- **结果**：诊断构建实测监控页每 5 秒重绘 3–4 次 → **1 次**；稳态下每个 5 秒窗口的 CPU 中位数 263 ms → 188 ms
  （−28%）。发布构建实测展开 60 秒 **2.8%**（修复前 5.21%，重做前 3.82%）。
- **没做的**：展开态剩下的大头是后台采样（温度 / 进程榜，非管理员时温度一条也读不到，照样每 1.4 秒采一次），
  约 1.5–2%；面板挂 `BitmapCache` 只在身后有动画时才有收益。两样都没动。

### 设计规则（细目见 `SOURCE-README.txt` 的"界面设计系统"一节）

- 一套主题 = 近黑中性色 + **一个**强调色 + 状态色。数据不按指标配色。
- 强调色只给主角和选中态：CPU 主读数、面板顶部那束辉光、选中的电源计划。其余读数是中性色，
  只有 ≥70% / ≥90% 才换成状态色 —— 告警是画面里唯一跳出来的颜色。
- 发光只给上面三处。试过给页签挂辉光滤镜（DropShadowEffect）：软件渲染下图标被重新采样，强调色发灰、边缘发糊，已撤。
- 数据用等宽体（Consolas + 微软雅黑回退），中文用界面字体。面板字号只用 36 / 17 / 12 / 11 四档。
- 面板里不许放默认模板的 WPF 控件，图标不许用 emoji。
- 浅色主题不发光、不铺网格；像素主题不铺网格、保持直角。
- HeiGe 配方里没做的三样：极光渐变文字（容易发腻）、呼吸的状态点（要持续重绘，与第九节的降耗冲突）、

### 1. WPF 软件渲染落地（App.OnStartup 第一行，`RenderOptions.ProcessRenderMode = SoftwareOnly`）

原理：本应用只有 `AllowsTransparency` 的分层窗口，永远用不上硬件加速，WPF 却为它创建 D3D 设备，
把 Intel 显卡驱动的两百多兆拉进进程。关掉硬件路径，这些全部消失。

| 实测（同机同场景，普通权限） | 硬件渲染（十节 final） | 软件渲染 | 变化 |
|---|---|---|---|
| 启动峰值工作集 | 245.7 MB | **126.7 MB** | **−119 MB**（第九节预估 −57 MB，实际省得更多；提交内存 174.2 → 59.3 MB） |
| ws@25s / commit@25s | 243.3 / 168.7 MB | 124.6 / 57.1 MB | 常驻内存减半 |
| 收起态空闲 40s | 5.87%（80s 对齐 4.4%） | 4.83% | 噪声内持平 |
| 展开 60s | 2.8% | 4.75% | **+2pp 单核**（栅格化从渲染线程落到 UI 线程；大头是毛玻璃每 0.125s 触发的整面重绘） |
| 收起后 10s | 2.91% | 1.38% | 反而更低（渲染线程没了，空转也少了） |
| 真实窗口截图 | — | 监控页 / 读数带画面完好，文字清晰 | 抗锯齿亚像素差异（约 1% 像素，放大 5 倍才看出）；不透明对话框 ClearType → 灰度 |

- 代价已在第十节"没有做"里预告过，用户拍板接受；**回退 = 删掉 App.OnStartup 里那一行**。
- 实现备注：`RenderMode` 枚举在 `System.Windows.Interop`（不在 Media，编译器指的路）；必须设在创建任何窗口之前。
- 收起态空闲没有回退 —— 第九、十节的降耗成果与软件渲染兼容。

### 2. AMD SMN 直读首启自动开启（只做一次）

规则钉在 `SmnChannel.AutoEnableOnFirstRun(isAmdCpu)`（纯函数，有测试）：**只有 AMD 机器**首次启动把
`EnableSmnDirectRead` 置为开；其余机器保持关闭。执行点在 App.OnStartup（"SMN 自动开启"一步，岛体窗口
创建之前），落定后写 `Settings.SmnAutoDone = true` 并立即存盘，**此后不再自动改** —— 用户在设置里关掉
（包括 AMD 用户）就是关掉；「全部重置」不重置 SmnAutoDone，不会复活它。

- 为什么只 AMD：SMN 是 AMD 专有寄存器，Intel 上零收益纯风险（五节的三次蓝屏）；而 AMD 上 LHM 读不到
  温度的机型（Family 0x10–0x16）只有这条路能出读数，让用户去设置深处找"高风险实验功能"开关不现实。
- 安全边界不变：真正的闸门仍是 SmnChannel.Ensure（未开启 ⇒ 不创建服务）+ InpOutSmnService 厂商门控
  （非 AMD ⇒ LoadLibrary 之前返回）+ 只认 0xE0000000；而且温度服务只在常规路径读不到时才尝试它。
- **本机（Intel）遗留的"已开启"被这一次自动纠正回 false**：真实 settings.json 里
  `EnableSmnDirectRead: true → false`、新增 `SmnAutoDone: true`，crash.log：
  `[1:56:29] SMN 自动开启（只此一次）：CPU=非 AMD，EnableSmnDirectRead True → False`。
- 设置窗口的提示文案同步改了（说明自动开启只一次、关掉不复活）；SOURCE-README 的温度链路一节同步。

### 验证

- 门禁：0 警告 0 错误，测试 242 条全过（新增 2 条：首启自动策略 Intel 不开 / AMD 开）。
- 实机验证（上表数字来自两次完整运行）：真实窗口截图正常、SMN 自动纠正落盘、日志有记录。

## 十二、设备电量增强 —— 2026-11-25（参考 ai-periph-monitor）

用户给了 [ai-periph-monitor](https://github.com/Xueluoa1/ai-periph-monitor)（雪落a 的 Windows 无线外设电量
监测工具，Python/tkinter，MIT）。它按**品牌协议**直读 2.4G/HID 外设电量（57 组 VID/PID 条目），蓝牙走系统
上报，XInput 手柄报档位，低电量提醒，托盘电量图标。方法论值得抄：只认 VID/PID+接口+有效回包、读回核对、
不把缓存当现值、未知回复不伪装成电量。

### MyIsland 原状与本机探测

DeviceService 只有两条 WMI 数据源（Win32_Battery 笔记本电池 + MSBatteryClass Windows 上报的蓝牙电量）。
探测本机：笔记本电池 100%；一台**联想 BLE HID 设备（ThinkBook Bluetooth Mouse）Windows 没有为它上报电量**
—— 设备页一直只显示笔记本电池；HID 列表全是内置设备，没有 2.4G 外设、没有手柄。

### 改了什么

| # | 位置 | 内容 |
|---|---|---|
| 1 | `Services/BleBatteryService.cs`（新） | **BLE GATT 电量直读**（Battery Service 0x180F / 0x2A19，Windows.Devices.Bluetooth，零驱动）：补 MSBatteryClass 不上报的蓝牙设备。节流：成功后 10 分钟不重读；缓存 30 分钟，过期即消失（不显示旧值）；读不到/回包非法不进列表。名字解析：条目 ItemNameDisplay → 父容器 Name → 兜底"蓝牙设备"；类型按名字关键词猜，猜不出标"蓝牙设备"（kind=ble），不硬安 |
| 2 | `Services/XInputService.cs`（新） | **XInput 手柄档位**（xinput1_4.dll，最多 4 个槽位）：空/低/中/满 → 界面画档位文字，**不换算百分比**（换算就是伪装）；电量环按档位近似取比例。没有手柄/没有 dll 返回空列表，UI 自然不显示 |
| 3 | `Services/DeviceInfo.cs`（拆出） | DeviceInfo 加 `LevelText`（非 null = 档位设备：界面显示文字，Percent 只是画环比例，不参与低电量提醒）。挪成独立文件的理由同 ThermalSnapshot：测试工程要链接 |
| 4 | `Services/DeviceService.cs` | 合并四条数据源；新增 `BackgroundWatch`（低电量提醒开着且没人看设备页时退到 **5 分钟一轮慢轮询**，否则提醒永远没有新数据；视图在看仍是 30s）；`Poke()`（托盘菜单打开时补一拍）；`LogLine/LogLineThrottled` 给 BLE 用 |
| 5 | `Controls/DevicesPage.cs` + `IslandCanvas.DrawDevices` | 档位设备画档位文字（20px/12.5px，分级配色照旧）；"蓝牙设备"成为合法类型标签（不再错标"本机电池"） |
| 6 | `Controls/IslandWindow.xaml.cs` | **低电量提醒** CheckBatteryAlert：低于阈值弹活动浮条（复用高温告警的浮条体系，图标圆红色），同一台设备 60 分钟最多一次；只对有百分比的设备生效 |
| 7 | `App.xaml.cs` | 托盘右键菜单加"设备电量"子菜单（打开时刷新，先显缓存再后台补一拍） |
| 8 | `Settings` + 设置窗口 | 低电量提醒开关（默认开）+ 阈值（默认 20%，夹到 5..50），放在"监控"卡片；全部重置回到出厂值 |

## 九、跨端一致性对齐（2026-11-24 ~ 2026-11-26，六轮）

### 为什么做这件事
前几轮下来，两端的「功能行为一致」是**靠人记**的：清单、文档、代码各写一份，改一处忘另一处。
这轮实测接连推翻了好几条自己写下的记录。基准是**以 mac 版现有实现为准**，但
**平台专属能力不互相搬运**、**呈现规则统一、差异公开在能力清单里**，
外加一条硬红线：**不伪装** —— 读不到就是「未知」，绝不用 0 / 默认值 / 换算百分比充数。

### 六轮做了什么

| 轮次 | 主题 | 关键交付 |
|---|---|---|
| 一 | 外设电量 | HID 访问层 + 三层校验 + 数据驱动协议表；联想 Idea5003 实测 58%（**推断值**） |
| 二 | CPU 温度口径 | 分层匹配（Package 优先、排除 Distance to TjMax 等干扰项）；本机 49 → 58 |
| 三 | mac 对齐 | 共享 HID 报告描述符解析器 + 两个原生探针 + 温度口径统一 |
| 四 | 采集口径 | CPU 占用改 `% Processor Utility`（任务管理器口径，实测 27% → 49~66%）、频率改 `Actual Frequency`、网速排除虚拟网卡 |
| 五 | 展开面板对齐 + 能力清单 | 顶栏 / 监控页 2×2 栅格 / 设备页卡片网格 / 剪贴板页；`CapabilityManifest` 成为两端唯一真相源 + 28 条漂移断言 |
| 六 | 把「看不见」变成看得见 | **两端离屏渲染探针**、协议表自检、多机型验证矩阵、跨端 token 用法门禁、GPU 显存口径 |

### 「发现自己的记录是错的」的那些时刻（实测，不是复盘）
- 文档写着「运行时长 = PDH System Up Time（不含休眠）」，**代码实际用的是 `Environment.TickCount64`**；
  那段 PDH 计数器**建了从不读、还不释放** —— 已删除，文档改为实际口径，两端同一实现。
- Windows 端注释写着「mac 的进程榜卡底同款」，**实际 mac 根本没有那行**。
- 能力清单里 Windows 独有的四个收起视图早已标了 `PlatformSpecific`，文档却还写成「两端差异待定」。

### 门禁从「能编译」升级到「看得见」
本机屏幕捕获在锁屏会话里只能拍到全黑 —— 此前「不崩」能验证，「画得对不对」无法验证。
新增两个**离屏渲染探针**（渲染的是**产品源码本身**，不是抄一份的副本）：
- `tools/visual-probe`（Windows，27 条不变量）：防全黑、栅格几何、文本越界、**卡内不压字**；
- `tools/avalonia-probe`（macOS，Avalonia Headless + 真实 Skia，33 条不变量）：**第一次真正看到 mac 端画面**。

第一次跑出真画面就抓到两个真问题：
1. **进程榜末行压在卡底信息行上**（explorer.exe / Teams.exe 压住「213 进程 · 1580 线程」）
   ⇒ 行数与行距改为从卡内可用高度倒推，并加两条离屏不变量（实测「改坏即红、修好即绿」）。
2. **应用图标首字母兜底两端用色不一致**（Windows `TextDim` vs mac `Text`）⇒ 改齐并纳入跨端 token 门禁。

### 两处误导性读数（不伪装红线的实际应用）
- **GPU 显存口径**：核显走 D3D 共享内存（已用 1.5 GB / 总量 17.95 GB ≈ 系统内存），
  界面却按独显显存口径显示 ⇒ 共享口径下**不显示那个总量**，只显示「1.5 GB 共享」。
- **协议表覆盖的静默失败**：用户改了协议表没生效时，工具反过来说「覆盖已生效」
  ⇒ 改为逐设备逐字段判定，不生效就明确报「不生效 / 哪里对不上」并拦门禁。

- **AMD / Intel 台式机 / 核显+独显 / 其它 2.4G 接收器**：`tools/verify-matrix.ps1` 逐轴专项检查。
- **SSD 温度（Windows）**：LHM 的 NVMe SMART IOCTL 在本机触发 0x1EA 蓝屏两次，**保持关闭** ——
  不为凑一个读数去冒蓝屏风险。

### 附带修掉的工程问题
- **门禁抖动**：`MemoryReclaim` 用例在满载机器上随机变红（上限 200ms 太紧，首次询问已超限就放弃）
  ⇒ 放宽上限，判定逻辑不变。
- **`.sh` 行尾**：新增 `.gitattributes` 钉住 `*.sh` 永远 LF（Windows checkout 不再转 CRLF，mac 上才不会报 `not found`）。

## 十、跨端一致性对齐 · 配色与默认视图（2026-11-26）

### 这轮用户拍板的四件事
1. **配色可读性**：各设平台门槛并加门禁，**不改任何具体色值**。
2. **默认收起视图**：两端**统一为 clock（时间胶囊）**。
3. **Windows 侧死设置 `DecorNotch`**：声明为 mac 专属并进能力清单。
4. 本轮改动推送 `origin/main`。

### 1. 先把"两端配色为什么不一样"查清（此前没查过）
- **三层结构**：① 12 个同名语义 token 两端**取值全不同**（暗色科技 vs Apple 系统色）；
  ② **配色策略**不同：mac = **按资源配色**（6 个固定色相，且独立于主题），
  Windows = **按分级配色**（正常 = Accent，≥70% = Warning，≥90% = Up，温度 ≤70 用文字色）；
  ③ mac 独占 `elevated`/`fill`/`selection` 三个材质 token，Windows 独占 `square-corners`（bool）。
- 9 个主题名两端完全相同，但**同名主题色值不同**（GitHubDark：mac `#0D1117`+`#2F81F7` / Windows `#0A0D12`+`#58A6FF`）。

### 2. 挖到的真问题：mac 端一条对比度断言都没有
把 Windows 端的门槛（正文 ≥7:1、次要 ≥6:1、三级 ≥4.5:1、强调 ≥4.5:1、状态色 ≥3:1）套到 mac 的 9 套主题上：
**9 套全不过**，三级文字最差 **2.50:1**（Light 主题）—— 而三级文字正是**底部状态行（9px）**的颜色。
根因不是"mac 配色差"，而是测试工程只链了 Windows 的 `Theme.cs`（mac 的 `Themes.cs` 依赖 Avalonia，进不了零依赖测试工程）
⇒ **mac 端可读性此前完全裸奔**。
**修法**（不改色值）：新增 `Island.Core/Capabilities/ThemeContrastGate.cs`（门槛数据 + WCAG 计算，纯 .NET），
门槛**按平台各设**（mac 取当前设计的实测基线再留 0.1 余量）；
新增 `tests/Island.Tests/ThemeContrastTests.cs`：**静态解析**两端主题源码 → 逐套主题逐 token 比对，
顺带守住"两端 `ByName` 的主题名集合必须一致"（此前只是恰好一样）。
Windows 端 `DesignSystemTests` 也改为从同一份清单读门槛 ⇒ **门槛只有一处定义**。

### 3. 默认收起视图统一为 clock
两端共用同一个 `Settings` 类 ⇒ 改 `Settings.CompactView` 默认值一处即两端生效。
顺带修掉一处旧不一致：mac 画布兜底默认是 `clock`、Windows 读的是 `dash`（同一个键两端指向不同默认值）。
**连带后果**：默认视图从此是 clock，而两端探针此前只覆盖 dash ⇒ **默认视图反而没有门禁**，
本轮给两端探针补上 clock 视图的像素不变量（非全黑 / 高亮墨迹 / 时间与网速画成两段 / 不越出宿主宽度）。

### 4. DecorNotch 声明为 mac 专属
登记进 `CapabilityManifest` 的 **decor 组**（`notch-fusion` / `PlatformSpecific` / `MacOnly`），
并加**反漂移门禁**：`src/Island.App` 里不得出现 `DrawNotchBody` 实现
（真画出来了就说明清单该改，而不是让差异偷偷溜进来）。

### 改坏即红（都做过实测，不是"应该会红"）
- mac Light 的三级文字调亮一档 ⇒ **可读性断言红**。
- mac 的 `ByName` 去掉一个主题 ⇒ **主题名一致性断言红**。
- clock 的宿主宽度压到 60（内容被裁）⇒ **clock 断言红**（墨迹聚簇只剩 1 段）。
  ⚠️ 第一版断言用的是**相对阈值**（`< 0.45w` / `≥ 0.55w`），宿主一窄阈值跟着缩 ⇒ 内容被裁也照样绿，
  是实测才发现的；改成**按产品常量 `CompactSpec.ClockGap` 的墨迹聚簇**才真正咬住。

### 还没对齐的（如实记，待产品拍板）

  剩余唯一差异是**上下行网速只有 Windows 有**（平台专属读数，公开在能力清单里）。
  - 文本格式（`"11月27日·周五"`、秒补零）抽到两端共用的 `Island.Core/Capabilities/ClockTextSpec.cs`，
    两端渲染代码都从它取（mac 端原本自己写了一份星期缩写，已删）。
  - 门禁 `tests/Island.Tests/ClockViewTests.cs`：文本格式 + 两端源码必须用同一份规格 +
    **宽度上限 ≥ 320**（这个上限同时是排版预算，给小了日期会被折成 "+N" 而**整个消失**）。
  - 实测：上限从 230 抬到 360；内容宽 ≈260（无天气），加天气 ≈308。
    ⚠️ 像素断言抓不住"+N 折叠"（实测：上限调回 230 时探针仍全绿）—— 所以必须有源码门禁 + 上限门禁双保险。
